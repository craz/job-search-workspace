# Процесс разработки Job Search

## 1. Назначение

Этот документ — источник правды для разработки `job-search-workspace` и
продуктовых репозиториев. Архитектурные границы определены в
[`ARCHITECTURE_PLAN.md`](ARCHITECTURE_PLAN.md).

Цель процесса: каждый этап заканчивается работающим, проверенным и независимо
поставляемым изменением. Работа ведётся небольшими вертикальными срезами:

```text
задача → исследование → spec/контракт → реализация → проверки → review → PR → release
```

## 2. Классы изменений

| Класс | Примеры | Обязательные артефакты |
|---|---|---|
| Малый | docs, локальный bugfix, тест | План в задаче, тест/проверка, diff |
| Обычный | новая команда, endpoint, UI-сценарий | Feature spec, тесты, PR |
| Архитектурный | граница репо, новый сервис, БД, breaking API | Feature spec, ADR, contract tests, rollout/rollback |
| Релизный | публикация версии или набора совместимых сервисов | CHANGELOG, compatibility check, tag, release notes |

Если класс неочевиден, используется более строгий.

## 3. Полный цикл задачи

### Этап 1. Triage и границы

До изменения кода зафиксировать:

- проблему и ожидаемый пользовательский результат;
- владельца изменяемого поведения;
- in scope и non-scope;
- критерии приёмки;
- риски для данных, секретов, HH и межсервисных контрактов;
- затрагиваемые репозитории и порядок их изменения.

Одна задача должна иметь один основной результат. Несвязанный рефакторинг
выносится в отдельную задачу.

### Этап 2. Исследование текущего состояния

Перед проектированием:

1. Проверить статус Git и существующие пользовательские изменения.
2. Найти текущую реализацию, тесты, миграции и публичные контракты.
3. Проверить актуальный API зависимости по официальной документации или
   установленному пакету.
4. Зафиксировать переиспользуемые решения и риски регрессий.
5. Не предполагать наличие файлов, сущностей или инфраструктуры, которых нет.

### Этап 3. Spec и contract first

Для обычных и архитектурных изменений создать spec по шаблону
[`docs/templates/FEATURE_SPEC.md`](docs/templates/FEATURE_SPEC.md).

До кода определить:

- User Story в формате «Как… Я хочу… Чтобы…»;
- Given/When/Then acceptance criteria;
- модель данных и владельца данных;
- HTTP/CLI интерфейсы, коды ошибок и идемпотентность;
- empty/error/degraded states;
- совместимость и версию контракта;
- наблюдаемость, миграцию и откат, если они нужны.

Архитектурное решение с альтернативами оформляется ADR по шаблону
[`docs/templates/ADR.md`](docs/templates/ADR.md).

### User Story и BDD

Каждая пользовательская возможность начинается с одной основной User Story:

```text
Как [роль пользователя],
Я хочу [выполнить действие],
Чтобы [получить результат или ценность].
```

User Story описывает роль, намерение и ценность, а не техническую реализацию.
Формулировки вроде «Как FastAPI», «Я хочу вызвать endpoint» или «Чтобы записать
строку в PostgreSQL» недопустимы, если это не реальное поведение внешнего
потребителя системы.

Acceptance criteria оформляются Gherkin-сценариями:

```gherkin
Feature: Управление вакансией

  Scenario: Добавление новой вакансии в воронку
    Given пользователь подготовил корректные данные вакансии
    When пользователь добавляет вакансию
    Then вакансия появляется в воронке со статусом "found"
```

Правила BDD:

- `Feature` соответствует возможности или ограниченному набору связанных User Stories;
- один `Scenario` проверяет одно наблюдаемое поведение;
- сценарий описывает бизнес-язык, а не классы, SQL и внутренние функции;
- happy path, ключевые ошибки, права/ограничения и идемпотентность оформляются
  отдельными сценариями;
- `Background` используется только для действительно общей предусловной части;
- `Scenario Outline` применяется для значимых наборов примеров без копирования;
- каждый scenario имеет стабильный идентификатор или тег User Story/задачи;
- изменение поведения начинается с изменения `.feature`, после чего тест должен
  падать до реализации и проходить после неё.

Gherkin-сценарии являются исполняемыми acceptance tests, когда поведение доступно
через публичный HTTP/CLI/UI-интерфейс. Чистые внутренние алгоритмы дополнительно
покрываются обычными unit-тестами; Gherkin не заменяет unit/integration/contract tests.

### Этап 4. План реализации

План должен быть decision-complete и содержать:

- последовательность изменений по репозиториям;
- изменение публичных интерфейсов;
- миграции и порядок развёртывания;
- unit, integration, contract, smoke и manual checks;
- безопасный откат.

Для изменения нескольких репозиториев сначала выпускается provider с обратно
совместимым контрактом, затем consumers, и только после этого удаляется старый
контракт.

### Этап 5. Реализация

Порядок внутри вертикального среза:

1. Domain/storage и миграция.
2. Application service.
3. HTTP API или JSON CLI.
4. Consumer/UI.
5. Наблюдаемость и документация.

Правила реализации:

- минимальный связный diff;
- без рефакторинга «заодно»;
- один репозиторий владеет данными и контрактом;
- нет импортов кода из service submodules;
- нет прямого доступа к чужой БД или volume;
- секреты не попадают в код, image, логи и fixtures;
- долгие HH/Scoring-операции имеют status/cancel и не удерживают агентскую сессию.

### Локальная среда и live development

Docker Compose остаётся основным способом запуска системы. Для Python-команд,
которые выполняются на хосте (линтеры, генераторы, служебные скрипты), основной
интерактивный путь — `direnv`, а независимый fallback —
`scripts/ensure-venv.sh` и Make-цели.

Каждый Python-репозиторий содержит безопасный коммитящийся `.envrc`, который:

- создаёт `.venv` при первом входе в каталог;
- автоматически добавляет `.venv/bin` в `PATH`;
- выставляет `VIRTUAL_ENV`, поэтому shell и IDE видят активное окружение;
- опционально загружает некоммитящийся `.env.local` через `dotenv_if_exists`;
- не содержит секретов и не запускает Docker или сетевые сервисы.

После первого клонирования пользователь один раз выполняет `direnv allow`.
Повторная активация происходит автоматически при `cd` в репозиторий, а при
выходе из каталога окружение автоматически выгружается.

Make-цели и CI не полагаются на shell activation. Они используют
`scripts/ensure-venv.sh`, который:

- автоматически создаёт `.venv`, если её нет;
- устанавливает зависимости из lock-файла при первом запуске или его изменении;
- никогда не требует ручного `source .venv/bin/activate`;
- не изменяет глобальный Python;
- хранит `.venv/` вне Git.

Базовый `.envrc` продуктового репозитория:

```bash
if [[ ! -d .venv ]]; then
  python3 -m venv .venv
fi

export VIRTUAL_ENV="$PWD/.venv"
PATH_add "$VIRTUAL_ENV/bin"
dotenv_if_exists .env.local
```

Зависимости синхронизируются Make/ensure-venv по lock-файлу, а не при каждом
`cd`, поэтому вход в каталог остаётся быстрым и не выполняет сетевые операции.

Таким образом, интерактивный терминал не показывает постоянные напоминания о
неактивированном окружении, но `make test` продолжает работать в чистом shell,
CI и агентских командах без `direnv`.

Режим разработки запускается командой `make dev` в workspace:

- Core/Web стартуют с hot reload;
- изменения Python-кода перезапускают только изменённый development-контейнер;
- изменения frontend/template автоматически обновляют открытую страницу;
- изменения зависимостей, Dockerfile, Compose, env или миграций вызывают rebuild
  либо явный контролируемый restart;
- состояние в named volumes при reload/restart сохраняется;
- HH Chromium доступен через локальный noVNC, а Web — через локальный dev URL.

Перед завершением UI-задачи агент проверяет изменённый сценарий в live browser,
если браузер доступен. Если автоматическая проверка невозможна, в отчёте остаётся
точный manual QA checklist и причина, почему он не выполнен.

### Этап 6. Проверки

Минимальные локальные gates для изменённого репозитория:

```bash
make format-check
make lint
make typecheck
make unit
make integration
make contract
make bdd
make build
```

Запускаются только существующие цели; каждый продуктовый репозиторий обязан
реализовать этот интерфейс Makefile либо явно документировать неприменимые цели.

Дополнительно:

- `make smoke` — для HH, Ollama, Telegram и сетевых провайдеров;
- `make compose-smoke` — для изменений связки сервисов;
- Alembic upgrade на чистой БД и на предыдущей поддерживаемой схеме;
- backup/restore test для изменений хранения;
- manual QA по feature spec для пользовательского интерфейса/noVNC.

Тесты не используют реальные отправки HH/Telegram по умолчанию. Реальные smoke
являются opt-in, ограничены лимитами и пропускаются с понятной причиной при
отсутствии конфигурации. Warnings в CI считаются ошибками; подавлять их вместо
исправления причины нельзя.

BDD feature-файлы хранятся в `tests/features/*.feature`, step definitions — в
`tests/bdd/`. Для Python-проектов стандартным runner будет `pytest-bdd`, если в
конкретном репозитории ADR не зафиксирован другой совместимый инструмент.
Сценарии выполняются в CI командой `make bdd` и не обращаются к реальным HH или
Telegram без отдельного opt-in smoke-профиля.

### Этап 7. Review

Перед PR автор просматривает полный diff и проверяет:

- соответствие scope и acceptance criteria;
- трассировку User Story → Gherkin Scenario → исполняемый тест;
- архитектурные границы и владение данными;
- совместимость OpenAPI/JSON Schema;
- идемпотентность, timeouts, retries и ошибки;
- миграции и rollback;
- отсутствие секретов и персональных данных в логах;
- тесты критических и негативных сценариев;
- обновление README, spec, ADR и CHANGELOG.

Blocker и high findings исправляются до merge. Неустранённые замечания должны
иметь отдельную задачу и не могут скрывать нарушение acceptance criteria.

### Этап 8. Git и PR

- Основная ветка: `main`.
- Рабочая ветка: `type/short-kebab-scope`.
- Типы: `feat`, `fix`, `docs`, `refactor`, `test`, `build`, `ci`, `chore`, `perf`.
- Коммиты: Conventional Commits — `type(scope): subject`.
- Один коммит описывает один логический завершённый шаг.
- После успешных проверок агент автоматически коммитит завершённый шаг, если
  рабочий каталог является Git-репозиторием.
- Перед автокоммитом агент проверяет `git status` и diff, добавляет только файлы
  текущей задачи и не захватывает пользовательские или посторонние изменения.
- Если отделить изменения текущей задачи безопасно нельзя, автокоммит не
  выполняется, а причина сообщается пользователю.
- Автокоммит не разрешает автоматически push, создание PR или merge: эти действия
  выполняются только по явному запросу пользователя.
- Merge разрешён только при зелёных required checks и заполненном PR-чеклисте.
- Предпочтительный merge: squash для короткой ветки; rebase/merge — когда важно
  сохранить последовательность самостоятельных migration/provider/consumer шагов.

### Этап 9. CI

Каждый продуктовый репозиторий должен проверять на pull request:

1. format/lint/typecheck;
2. unit и integration tests;
3. BDD/Gherkin acceptance tests;
4. contract compatibility;
5. Alembic migrations, если репозиторий владеет БД;
6. сборку Docker image;
7. поиск секретов и уязвимых зависимостей;
8. smoke без реальных внешних отправок.

Workspace дополнительно проверяет `.gitmodules`, соответствие submodule HEAD
зафиксированным gitlinks, сборку Compose и сквозной сценарий Web → Core →
PostgreSQL.

### Документация как часть изменения

Документация обновляется в том же логическом шаге, что и поведение:

- README — назначение, quick start, команды, конфигурация и ссылки на подробности;
- feature spec — acceptance criteria и фактический статус;
- OpenAPI/JSON Schema — публичный контракт;
- ADR — существенные архитектурные решения;
- runbook — запуск, диагностика, backup/restore и восстановление после отказа;
- CHANGELOG — пользовательски значимое изменение;
- каждый модуль, публичный класс и публичная функция имеют содержательный
  docstring: назначение, значимые входы/выходы, побочные эффекты, ошибки и
  инварианты — насколько они не очевидны из сигнатуры;
- сложные приватные функции также получают docstring;
- inline-комментарии обязательны у опасных операций, неочевидных ветвей,
  совместимости, временных обходов и архитектурных ограничений;
- комментарии объясняют причины и ограничения, а не механически пересказывают
  код; устаревший комментарий считается дефектом.

Наличие docstring само по себе не является доказательством качества. Для
управляющего или интеграционного модуля документация в коде должна позволять без
контекста чата понять его место в системе, основной поток, внешние эффекты,
failure modes, safety guarantees и сознательный non-scope. Во время review
утверждения в комментариях сверяются с фактическими ветками реализации.

### Контекст AI-агентов

Корневой `AGENTS.md` и единственный глобальный Cursor rule содержат только
общесистемные ограничения: безопасность, границы репозиториев, gates и Git.
Инструкции для scripts, tests и docs располагаются в ближайшем вложенном
`AGENTS.md`; Cursor Rules подключаются по globs либо по релевантности. Приватные
AI-сессии исключены через `.cursorignore`, а environments, runtime/generated и
vendor trees — через `.cursorindexingignore`. Новый Always Apply rule требует
сначала доказать, что требование необходимо для любого запроса и не помещается в
существующий минимальный глобальный rule.

Изменение не считается завершённым, если команды, конфигурация или поведение в
документации расходятся с реализацией. Примеры команд по возможности проверяются
в CI или smoke-тестах.

### Этап 10. Release и rollout

- Версионирование: SemVer.
- Источник версии: Git tag `vX.Y.Z` каждого продуктового репозитория.
- Изменения описываются в Keep a Changelog.
- Breaking contract требует major version и migration guide.
- Сначала разворачиваются обратно совместимые providers, затем consumers.
- После rollout проверяются health/readiness, error rate, latency и критические
  бизнес-сценарии.
- Rollback возвращает предыдущие image tags. Необратимая миграция требует
  предварительного backup и явно описанной forward-fix стратегии.
- Workspace lock обновляется только после успешного integration smoke совместимого
  набора версий.

## 4. Definition of Ready

Задача готова к реализации, когда:

- определены результат, scope и non-scope;
- User Story содержит роль, действие и ценность;
- найдены затронутые репозитории и владелец данных;
- acceptance criteria описаны проверяемыми Gherkin-сценариями;
- публичные контракты описаны;
- рисковые внешние действия явно отмечены;
- для архитектурного решения принят ADR;
- нет открытого решения, которое придётся угадывать разработчику.

## 5. Definition of Done

Изменение завершено, когда:

- acceptance criteria выполнены;
- BDD-сценарии связаны с User Story и проходят в CI;
- diff не содержит несвязанных изменений;
- миграции и публичные контракты проверены;
- обязательные local/CI gates зелёные без warnings;
- документация и CHANGELOG обновлены;
- security/review findings устранены;
- rollout и rollback понятны;
- для multirepo-изменения проверен совместимый набор версий и обновлён workspace lock;
- итоговый отчёт перечисляет изменённые файлы, выполненные проверки и известные ограничения.

## 6. Стоп-условия

Работа останавливается до явного решения пользователя, если требуется:

- реальная отправка откликов или сообщений;
- изменение/удаление browser profile, токенов, volume или backup;
- destructive Git-команда;
- breaking contract без согласованной миграции consumers;
- расширение scope на другой продуктовый репозиторий;
- принятие продуктового решения, которого нет в spec;
- действие с секретами или персональными данными вне утверждённого контура.

## 7. Локальная история AI-сессий

Каждый пользователь репозитория может инициализировать приватное хранилище
platform session exports и summary-журнал командой:

```bash
scripts/init-ai-history.sh
```

Структура, правила derived-представлений и приоритет источников описаны в
[`docs/AI_HISTORY.md`](docs/AI_HISTORY.md). Механизм является частью репозитория;
пользовательское содержимое `.local/` никогда не коммитится.
